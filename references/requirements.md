# 软著规则摘要

本文件用于给使用该 skill 的代理提供软著申请和审查背景，不用于替代正式申报系统说明。

## 2026-03-15 新规（最重要，必须读）

中国版权保护中心 2026-03-15 起施行的新版《软件著作权登记申请表》带来以下变化，直接影响本 skill 输出材料的设计：

1. **手抄独立开发承诺**：申请表签章页新增一段必须手抄的承诺——"本软件确系人的独立开发，未使用 AI 开发编写代码、撰写文档或生成登记申请材料；如有失实或欺骗，自愿承担列入版权登记失信名单及个人征信记录的后果。" 失信记录同步至国家征信，影响信贷 / 招投标 / 高消费。
2. **AI 查重**：审核引入大模型生成痕迹检测 + 跨申请人历史代码相似度比对。被识别即驳回或要求补正，多次违规进入失信名单。
3. **主要功能字数**：从 ≤200 字提升到 **500–1300 字**。（本 skill 验证器已强制。）
4. **源代码鉴别材料口径**：总行数 >3000 时提交前 30 页 + 后 30 页，**每页 ≥50 行（不含空行/无注释行）**；不得提交编译后/加密二进制；页码连续，前后页要从完整函数开头开始、以标志性语句结尾。注释占比不得超过 1/3。
5. **文档⇆代码强一致**：操作手册、设计说明书每个功能点必须有对应代码支撑；夸大功能、虚标功能、文档与代码字段不对齐都会触发补正。

### Skill 落地策略（已实现）

- spec 验证器拒绝任何 `Support\d+ / Demo\d+ / Sample\d+ / Placeholder\d+ / XxxSupport*` 等机械桩类命名。
- 验证器扫描 spec 自然语言段落与代码片段，命中"由 AI / ChatGPT / 大模型 生成"等字样直接驳回。
- 验证器拒绝跨模块重复 ≥4 次的同一方法签名、≥3 次的 240 字符近似块。
- 删除原有「附录 A 通用工具类」与自动追加的 `XxxSupport001/002/…` 占位类，代码总量完全由调用方真实代码决定（≥1800 有效行）。
- 引入 `variation_nonce`（默认时间戳）让相同 software_name 在不同次运行得到不同主题/截图/导航，降低人工抽审时"几份材料一个模子"的观感。

### 软件本身含生成式 AI 的额外材料

当软件产品本身使用生成式 AI（智能客服、AIGC 文案、智能审核、推荐生成等）时，除三件套外还需提交 **《XX 软件合法合规及原创性声明文件》**，对应本 skill 的 `genai_declaration` 字段。文档结构（参照"国资监管大模型软件合法合规及原创性声明文件"范式）：

1. **声明主体信息**：主体名称 + 统一社会信用代码 / 组织机构代码（个人填身份证号）+ 可选联系方式
2. **软件作品相关声明**：
   - 合法合规声明（遵守《网络安全法》《数据安全法》《个人信息保护法》《生成式人工智能服务管理暂行办法》）
   - 原创性声明（代码 / UI / 架构 / 数据库结构独立研发；引用开源组件遵守开源协议）
3. **生成式人工智能服务相关声明**：
   - 合法合规声明（训练数据来源合法、个人信息保护、算法不歧视）
   - 服务规范声明（用户告知、内容审核、投诉举报渠道）
4. **生成内容相关声明**：
   - 合法合规声明（不含 6 类禁止内容）
   - 原创性及权利归属声明（不简单复制；纠纷依法担责）
5. **其他声明** + 签章页：声明主体盖章 / 签字 + 日期

> 注意：申请表手抄承诺"未使用 AI 撰写代码 / 文档 / 材料"是申报过程的承诺；本声明是产品形态的披露。两件事并行存在，互不冲突。签章页须打印后用黑色中性笔亲笔签字或加盖公章，禁止打印代签或电子签。

### 调用方（LLM）必做

- 模块拆分要贴系统业务；类名、方法名、字段名都用真实领域名词。
- 每段代码加入可追溯的业务注释（约束、状态机、SLA、踩坑），但避免逐行解释。
- 申请表 / 操作手册 / 代码三份内容必须互相印证：手册说能干 X，代码就要有干 X 的方法，申请表"主要功能"列出来的也要在手册章节里出现。
- 不在任何输出里承认或暗示使用 AI；如果输出里出现这种字样，验证器会直接 fail。
- 历史申请过的代码不要复用——新规会跨申请人比对。


## 核心材料

根据《计算机软件著作权登记办法》，软件著作权登记通常涉及三类核心材料：

- 软件著作权登记申请表
- 鉴别材料
- 相关证明文件

鉴别材料通常包括：

- 源程序
- 文档

常见文档形态包括：

- 用户手册
- 操作手册
- 设计说明书

## 常见审查点

代理在生成材料时，应优先避免这些问题：

- 软件名称在申请表、说明书、代码文档中不一致
- 主要功能、开发目的、技术特点之间前后矛盾
- 文档主题与软件名称不匹配
- 代码文档里残留旧项目名称、旧包名、旧实体名
- 文档过短或结构过散，无法支撑系统完整性
- 内容明显套壳、与系统简介无关、复用痕迹过重

## 鉴别材料常见口径

《计算机软件著作权登记办法》规定了源程序和文档的基本提交口径。实务中常见理解是：

- 源程序和文档通常按前、后各连续 30 页准备
- 总页数不足 60 页时，可以全部提交
- 申请表、说明书、代码文档中的软件名称应保持一致

本 skill 参考这些口径生成固定格式的材料，但不负责在线申报和主体证明文件。

## 补正与不予登记风险

在规则和常见办理说明中，以下情况容易触发补正或影响登记：

- 申请材料不齐全或填写不规范
- 申请人信息、权属依据、名称或版本信息不一致
- 提交材料存在明显权属争议
- 软件名称或内容违反相关规定
- 鉴别材料无法识别软件独创表达

## 本 Skill 的定位

本 skill 的定位是：

- 快速生成三件套草案
- 保持模板风格统一
- 降低手工改写工作量

本 skill 不处理：

- 在线正式填报
- 主体身份证明
- 委托书或合作开发协议
- 法律真实性核验
